# Task C — Xero Integration Review

**Assumptions.** A confidential server app uses the OAuth 2.0 authorization code flow and calls Accounting API v2.0 over HTTP (`https://api.xero.com/api.xro/2.0`). The design is independent of a specific SDK. The outbound flow creates one sales invoice (`ACCREC`) per internal order per tenant. Scope examples assume the granular scopes available to current web apps. [OAuth 2.0 overview](https://developer.xero.com/documentation/guides/oauth2/overview) · [Scopes](https://developer.xero.com/documentation/guides/oauth2/scopes/)

## C1 — Connection verification

1. On first connection, verify the callback `state` against the initiating session and exchange the code for tokens using the registered redirect URI. Check that an access token was issued, record its expiry and verify the granted scopes. Use `offline_access` for background work, `accounting.settings.read` for the organisation probe and `accounting.invoices.read` for invoice reads. Flows creating invoices need `accounting.invoices`. The exchange proves the OAuth client obtained a grant with identifiable permissions. [OAuth 2.0 overview](https://developer.xero.com/documentation/guides/oauth2/overview) · [Token types](https://developer.xero.com/documentation/guides/oauth2/token-types/) · [Scopes](https://developer.xero.com/documentation/guides/oauth2/scopes/)
2. With that access token, call `GET https://api.xero.com/connections`. Require a `200` with the intended `ORGANISATION` tenant. Match it to the user's selected organisation and persist its `tenantId` and connection `id` against the internal organisation and grant. During onboarding, `authEventId` can narrow the list to the current authorization event. This proves the connection is visible to the bearer. An empty list or a missing target stops onboarding. [Xero Tenants](https://developer.xero.com/documentation/guides/oauth2/tenants/)
3. Call `GET /Organisation` on the Accounting API with the same bearer and `Xero-Tenant-Id: <tenantId>`. Check the `200` response and returned `OrganisationID` against the intended organisation. This verifies that the application actually sent a usable tenant header and can read that organisation. The first invoice read will exercise invoice-specific permissions. [Organisation endpoint](https://developer.xero.com/documentation/api/accounting/organisation/) · [Scopes](https://developer.xero.com/documentation/guides/oauth2/scopes/)

## C2 — Failure diagnosis

Start with the worker's exact request and token version. Compare the environment's app registration, grant, tenant mapping, API host, v2.0 path and HTTP method. Confirm the proxy or HTTP client forwards `Authorization: Bearer …` and `Xero-Tenant-Id` with the connection's `tenantId`. Check whether the target is still present in `/connections` using the same token as the failing call. Record the status, an allowlisted error code and any Xero correlation ID. [OAuth troubleshooting](https://developer.xero.com/documentation/guides/oauth2/troubleshooting/) · [Xero Tenants](https://developer.xero.com/documentation/guides/oauth2/tenants/)

- **401.** If `WWW-Authenticate` indicates insufficient scope, inspect the actual granted scopes and ask for renewed consent with the required permissions. If the bearer is expired or rejected, check that it is an access token issued for the configured app. Use or obtain a fresh token once for the same grant, then retry the read once. If refresh reports `invalid_grant` for the current stored token, or the organisation was disconnected, pause the tenant's jobs and request reconnection. [Xero Developer FAQ](https://developer.xero.com/faq) · [OAuth troubleshooting](https://developer.xero.com/documentation/guides/oauth2/troubleshooting/)
- **403.** Confirm the caller's `Xero-Tenant-Id` and selected connection, then check the authorizing user's current role and the organisation's access to invoicing. If the response is an HTML access-denied page, check the proxy and TLS configuration. Pause until the relevant access or configuration is corrected. [Accounting response codes](https://developer.xero.com/documentation/api/accounting/responsecodes) · [OAuth troubleshooting](https://developer.xero.com/documentation/guides/oauth2/troubleshooting/) · [Organisation endpoint](https://developer.xero.com/documentation/api/accounting/organisation/)
- **404.** Check host, version and route first. If `GET /Invoices?page=1&pageSize=1` succeeds but `GET /Invoices/{InvoiceID}` fails, verify the stored Xero invoice ID and that it belongs to the selected organisation. A record from demo or another tenant can fail this lookup. Keep the job pointed at the configured tenant while investigating. [Accounting response codes](https://developer.xero.com/documentation/api/accounting/responsecodes) · [Invoices endpoint](https://developer.xero.com/documentation/api/accounting/invoices)

## C3 — Incremental synchronisation

1. **Persist progress per tenant.** Use one active invoice scan per tenant and persist the last completed UTC watermark. At the start of a run, save a fixed upper cutoff based on the current UTC time with a small clock-skew allowance. Page through `GET /Invoices?page=1&pageSize=100` and subsequent pages with `If-Modified-Since` set a little before the last watermark, rounded down to a whole UTC second. Apply records with `UpdatedDateUTC` before the cutoff and leave newer records for the next run. Use the documented timestamp and invoice ID ordering and page metadata. Partition a large initial backfill into bounded invoice `Date` ranges using Xero's supported filters. [Accounting requests and pagination](https://developer.xero.com/documentation/api/accounting/requests-and-responses/) · [Invoices filters and ordering](https://developer.xero.com/documentation/api/accounting/invoices)
2. **Make page writes replayable.** Upsert by `(tenant_id, InvoiceID)` and retain the remote status, timestamp and a fingerprint of the fields used locally. Skip unchanged duplicates and prevent older records from overwriting newer ones. For equal timestamps with changed data, verify the current details before replacing the local record. Commit each page transactionally. If fetching or processing a page fails, leave the completed watermark in place and replay the interrupted window or partition from page 1. Advance the watermark to the fixed cutoff only after the entire run is durably processed.
3. **Reconcile independently of the cursor.** Page numbers can shift during concurrent edits. If a scan shows drift such as the same invoice on different pages, replay that window before advancing. If the problem persists, reschedule or split the window and alert on a stalled watermark. Also schedule rolling reconciliation of invoice date ranges without `If-Modified-Since`, because paging drift can be silent and some changes, such as certain due-date edits, do not bump `UpdatedDateUTC`. Compare IDs and relevant fields, verify missing or differing records with a detail GET, and apply explicit status changes such as voiding. [Accounting requests and modified resources](https://developer.xero.com/documentation/api/accounting/requests-and-responses/) · [Invoices endpoint](https://developer.xero.com/documentation/api/accounting/invoices)

## C4 — Rate limits

- On `429`, use `X-Rate-Limit-Problem` to identify the affected quota. Persist a shared cooldown for that tenant, or for the whole app if the app-wide quota was hit. Reschedule the job no earlier than `Retry-After` seconds, adding bounded jitter to spread restarts. If the header is unavailable, use capped exponential backoff with jitter. Release the worker slot while waiting. [Xero rate limits](https://developer.xero.com/documentation/best-practices/api-call-efficiencies/rate-limits/)
- Enforce concurrency and request budgets across workers. Use a per-tenant semaphore below the documented five in-flight requests and an app-wide limiter. Track `X-MinLimit-Remaining`, `X-DayLimit-Remaining` and `X-AppMinLimit-Remaining` to slow jobs before exhausting their quotas. Configure the tenant daily budget for the actual tier. During a tenant cooldown other tenants can continue within the app-wide budget. [Xero rate limits](https://developer.xero.com/documentation/best-practices/api-call-efficiencies/rate-limits/)
- Cap attempts and elapsed time for transient failures. A known daily reset may require a scheduled continuation after cooldown, without polling the API. Retry network errors and transient `5xx` on safe reads. Apply C5 to uncertain writes, including a retry deferred past the key lifetime. Validation errors, missing scopes, persistent `401`, `403` and confirmed `404` require a data, grant or configuration change before resuming. Alert on exhausted retry budgets. [Accounting response codes](https://developer.xero.com/documentation/api/accounting/responsecodes) · [Idempotent requests](https://developer.xero.com/documentation/guides/idempotent-requests/idempotency/)

## C5 — Data integrity

1. In the same local transaction as scheduling the export, persist one operation per `(tenant_id, order_id)`. Store a stable, reserved sales `InvoiceNumber`, the exact request payload and an app-unique `Idempotency-Key`. Claim the operation atomically and record the first dispatch time before sending `PUT /Invoices`. On success, validate the returned invoice and save its `InvoiceID` together with the completed operation. A worker recovering an in-flight operation after a crash treats the outcome as unknown. [Invoices endpoint](https://developer.xero.com/documentation/api/accounting/invoices) · [Idempotent requests](https://developer.xero.com/documentation/guides/idempotent-requests/idempotency/)
2. On a timeout, mark the outcome unknown. Within Xero's six-minute key lifetime, retry the exact request with the same key and a safety margin before expiry. If the response was lost after creation, the replay can return the cached result. Errors can also be cached. If the key has expired or retries keep returning an error, use an exact `InvoiceNumbers` lookup in the same tenant before issuing another create. [Idempotent requests](https://developer.xero.com/documentation/guides/idempotent-requests/idempotency/) · [Invoices filters](https://developer.xero.com/documentation/api/accounting/invoices)
3. If the lookup finds a match, verify its sales invoice type, contact, currency and expected amounts, then link its `InvoiceID` locally. A mismatch or a negative lookup while the original outcome remains uncertain goes to bounded reconciliation and then manual review. Resume creation with a fresh key and the same reserved invoice number only once the earlier attempt is confirmed to have had no effect. [Invoices endpoint](https://developer.xero.com/documentation/api/accounting/invoices) · [Idempotent requests](https://developer.xero.com/documentation/guides/idempotent-requests/idempotency/)

## C6 — Observability and security

- **Logs and traces.** Record the job and trace IDs, environment, a pseudonymous internal tenant reference, route template, status, latency, attempt number, outcome, page or watermark, and `Xero-Correlation-Id` when supplied. Use an allowlist for error fields. Exclude tokens, authorization codes, client secrets, authorization and cookie headers, raw request and response bodies, and invoice or contact data. [Xero rate-limit header example](https://developer.xero.com/documentation/best-practices/api-call-efficiencies/rate-limits/)
- **Metrics and alerts.** Measure request latency and errors by endpoint and status class, remaining quota, `429` rates, refresh failures, oldest queued job, watermark lag and the age of unresolved invoice writes. Alert on sustained auth or rate-limit failures, stalled syncs and growing reconciliation backlogs. Keep job and tenant IDs in structured logs instead of metric labels.
- **Credential lifecycle.** Store environment-specific client secrets in a managed secrets store. Encrypt tokens at rest with managed keys, restrict decryption to the authorized workers and audit access. Serialize refreshes per OAuth grant, including when a grant serves multiple tenants. Re-read the token version under the lock and atomically replace access token, refresh token and expiry. Xero documents a 30-minute grace period for retrying the prior refresh token if the response was lost or could not be saved. Rotate client secrets through a controlled deployment, and revoke affected grants on disconnection or exposure. [Managing tokens and IDs](https://developer.xero.com/documentation/best-practices/data-integrity/managing-tokens/) · [Token rotation](https://developer.xero.com/documentation/guides/oauth2/token-types/) · [Managing connections](https://developer.xero.com/documentation/best-practices/managing-connections/connections/)
